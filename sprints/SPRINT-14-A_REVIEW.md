## 3. رحلة المتصفح الحية

المسبار يستعمل integration_app ومستودعات PG وArgon2 وJWT الحقيقيين، مع mock لشبكة Meta فقط. لا ينادي API مباشرة في سيناريو الرحلة؛ استعلامات SQL لاحقة تتحقق من آثار أفعال المتصفح.

1. GET register 200 ⇒ POST register 303 إلى `/app/`؛ ثلاث كوكيات جلسة. تتبّع النداءات أثبت **غياب نداء auth/login ثانٍ**.
2. GET home 200 وشريط account=true؛ POST brand بالاسم «مطعم المراجعة» والقطاع restaurants ⇒303 settings#connect. PG يثبت slug مطابقاً `brand-[0-9a-f]{8}` وقطاعاً محفوظاً في brand_profiles.
3. POST connections/start ⇒303 إلى Meta؛ أخذ state الصادر فعلياً ثم GET bridge بكود صناعي ⇒303 pages؛ صفحة الاختيار 200 بصفحتين؛ POST selection ⇒303؛ **PG يثبت صفحة مختارة واحدة**.
4. POST whatsapp ⇒303 ثم POST rotate ⇒303؛ الحساب active والاعتمادات مشفرة في PG. HTML بلا أسرار الطلب؛ الشريط channel=true وdraft=false. ثلاثة POSTs محمية بلا CSRF ⇒403.
5. خمس شاشات حتى القناة (register/home/settings/pages/settings)، دون نشر أو اعتماد تلقائي. **اختبار اصطناعي بمزود وهمي، وليس TTFV لعميل حقيقي أو إثبات ربط حي مع Meta/WABA أو صلاحيات App Review.**

## 4. حالات الحافة — الثلاث مثبتة حياً

### S14A-1 — ضياع state بعد متابعة GET صفحة الدخول

- المرجع: `src/ui/session.py:73-76` و`src/ui/router.py:1262-1277`.
- `login_target` يركّب `?next={next_path}` دون quote؛ `&state=` يصبح معاملاً مستقلاً لصفحة الدخول.
- المسبار: بدء OAuth بحساب حقيقي ⇒ مسح الكوكيات ⇒ bridge 303 ⇒ **اتباع GET login** ⇒ hidden next يحوي code ولا state ⇒ POST login 303 ⇒ bridge 303 مع `flash=missing_parameters` ⇒ home 200. **PG: connections=0**.
- يفشل بأمان قبل Graph ولا يتجاوز state verifier، لكنه يقطع رحلة الربط. إغلاق إلزامي B-0.1 مع اختبار كل التحويلات؛ اختبار المنفذ القديم اكتفى بـLocation.

### S14A-2 — نموذج تحديث حساب WhatsApp نشط يصطدم بـ409

- `settings.html:38-62` تعرض wa-connect داخل details لأي حساب؛ `router.py:1470` يرسل POST إلى connect.
- `whatsapp/service.py:117-120` يرفض active بـ`whatsapp_account_exists`؛ إعادة الربط للـdisabled فقط، ولا زر تعطيل في الواجهة.
- المسبار: ربط 303 ⇒ تدوير 303 ⇒ تحديث **409 برسالة عربية**؛ الحساب يبقى active، دون فقد بيانات أو تسرب أسرار.
- B-0.2: زر disable عبر DELETE القائم، active يعرض rotate/disable، وdisabled يعرض reconnect؛ اختبار دورة كاملة بنفس account id. لا اختراع PUT account.

### S14A-3 — مفتاح password_too_weak غير مستخدم لرفض422

- `router.py:421-430` يختار http_422 لأي detail قائمة؛ RegisterRequest يرفض القصيرة والمطابقة للبريد.
- المسبار: قصيرة ثم password=email ⇒ **422 في الحالتين مع error.http_422 وغياب error.password_too_weak**. الخلفية ترفض القيم بشكل صحيح؛ العيب في الرسالة.
- B-0.3: تصنيف أخطاء التحقق المحددة، دون عرض input أو نسخ قواعد auth؛ البريد غير الصالح لا يصنّف كلمة مرور ضعيفة.
